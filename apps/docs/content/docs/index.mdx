Open Design Tokens checks design token files against the [Design Tokens Format Module 2025.10](https://www.designtokens.org/tr/2025.10/format/) and the [Color Module 2025.10](https://www.designtokens.org/tr/2025.10/color/), then lets you layer your own policies on top with a configurable linter.

It is built for the places where token files move between people and tools: CI on a pull request, a build step in a design-system repo, an editor integration, or a service that accepts uploads.

## Status

Beta. The validator is feature-complete for the 2025.10 specifications and tested against the spec text, and the public API is settled in shape. Versions stay on 0.x until the toolkit has seen real-world use; see [versioning](/reference/versioning) for what that guarantees.

## Design principles

- **The spec is the spec.** The validator reports what the normative text says, with errors for MUST violations and warnings where the spec says MAY or SHOULD. Where spec examples contradict the spec's own rules, the rules win and the examples are documented as [known spec issues](/concepts/spec-coverage).
- **Policy is separate.** Name lengths, naming styles, required descriptions: those are lint rules you configure, never validator behaviour.
- **Hostile input is normal input.** Token files are untrusted. There is no code evaluation, nesting is bounded, references never leave the document, and diagnostics are escaped. See [security](/concepts/security).
- **No runtime dependencies.** The published package depends on nothing.
